## Проблема, которую нужно решить

`orthoproto/align.py`'s `align_windowed()` подгоняет **независимый** rigid-fit (Kabsch, `fit_rigid3`) в каждом скользящем окне (12с, шаг 4с) между позициями одометрии FAST-LIVO2 и RTK-фиксами. Это работает разумно на прямых участках (невязка <0.15м по 2D на тестовых прямых, судя по `test_align.py`), но:

1. **На реальных данных остаточная невязка ~7-9м (до 17м max)** — либо реальное качество RTK/GPS в этом сегменте (fix-статус не записан, только позиция), либо чувствительность обычного МНК-фита к выбросам внутри окна (`fit_rigid3` не робастный).
2. **Во время резкого 180°-разворота одометрия FAST-LIVO2 дрейфует по Z в своей локальной системе координат** (см. докстринг `align.py`: "FAST-LIVO2 heading drifts during aggressive turns (observable in this capture on the 180-degree return)"). Так как Z-таргет в подгонке — константа (медиана RTK-высоты по всему сегменту, не по окну — умышленно, потому что RTK-высота в этом бэге "заморожена" на ~1155.6м и физически недостоверна, см. `dsm.anchor_to_dem`), окна вокруг разворота дают резко смещённую позу камеры (AGL после подгонки доходит до 387м при реальных ~80м).
3. **Итоговый эффект**: когда исходящий и обратный проходы разворота накладываются друг на друга в мозаике, несогласованность между независимо подогнанными окнами даёт "двоение"/размытие при бленде — именно это сейчас видно на мозаике `data/outputs/geoloc_capture_01_ortho/ortho_mosaic.png` (правая/верхняя часть чёткая, левая — размыта).

Уже пробовали (и это **не решило** проблему полностью, только смягчило симптом): фильтр `agl_max_m` отбрасывает кадры с явно неправдоподобной высотой ДО рендера — работает, но не лечит причину (независимость окон), и просто теряет ~52-69% кадров сегмента без объяснения, почему их поза вообще оказалась плохой.

## Задача

Заменить (или дополнить — решай по ситуации) независимые оконные Kabsch-подгонки в `align_windowed()` на **совместную (глобальную) оптимизацию** всей траектории сразу — по сути, маленький pose-graph / bundle-adjustment для одной последовательности:

- **Узлы**: поза (SE(3) или как минимум позиция+ориентация) на каждый временной срез — либо на каждом RTK-фиксе, либо на равномерной сетке ключевых кадров (решай сам, что проще реализовать надёжно).
- **Constraint 1 (относительное движение)**: между соседними узлами — относительная трансформация ИЗ САМОЙ ОДОМЕТРИИ FAST-LIVO2 (она очень точна на коротких базах, драфт накапливается медленно) как "мягкая пружина", сохраняющая локальную форму траектории даже там, где абсолютная привязка шумит.
- **Constraint 2 (абсолютная привязка)**: RTK-позиции (E/N, уже с исправленным свопом lat/lon — см. `geo.py`/`bagio.py`) как разреженные абсолютные ограничения, с **робастной функцией потерь** (Huber/Tukey/или явный outlier rejection типа RANSAC на препроцессинге) — сейчас обычный МНК одного выброса в окне достаточно, чтобы испортить всю подгонку.
- **Z по-прежнему не тянуть из RTK напрямую** (та же причина, что и сейчас — RTK-высота в этом бэге замороженная и недостоверная): либо не включать Z в constraint 2 вовсе (только E/N), либо использовать DEM-анкеринг (`dsm.anchor_to_dem`) как есть, уже после глобальной оптимизации.
- Реши сам: писать ли собственный Gauss-Newton/Levenberg-Marquardt на `scipy.optimize.least_squares` (нужно будет добавить `scipy` в зависимости `tools/orthoproto/pyproject.toml` — это нормально, но сделай осознанно, не тихой стороной), или другой подход — но БЕЗ тяжёлых новых зависимостей (никакого ROS/g2o/GTSAM, это чистый Python offline-прототип).
- Итоговый интерфейс должен остаться совместим с `TransformSeries`/`AlignmentResult` (или явно замени на что-то не менее удобное) — `dsm.py` и `ortho.py` дальше по пайплайну используют `align.series.at(t)`/`.apply(...)`, ломать этот контракт без необходимости не стоит.

## Обязательные проектные инварианты (см. `project_geoloc_invariants`)

- Честный отказ лучше выдуманной позы — если оптимизация не сходится или данных в окне мало, это должно быть видно (например, через выросшую невязку/covariance), а не молча замаскировано.
- Пороги — в конфиг (`configs/orthoproto/geoloc_capture_01.yaml`), не хардкодить в коде (вес RTK-constraint'а, порог робастной функции потерь, шаг между узлами графа и т.п.).
- Детерминизм тестов по фиксированному сиду (`np.random.default_rng(N)` с конкретным N, как в существующих тестах).

1. **Юнит-тесты** в `tools/orthoproto/tests/test_align.py` (расширь существующие или добавь новые) на синтетике, аналогично `_synthetic_path()` (там уже есть 180°-разворот с шумом) — но добавь сценарий с явными RTK-выбросами внутри одного окна и/или с реалистичным Z-дрейфом одометрии через разворот, и проверь, что новый глобальный fit не разваливается так, как разваливался независимый оконный (сравни невязку/устойчивость до и после).
2. **Прогон на реальных данных** — все три шага из корня репо:
   ```bash
   cd C:\Users\ilyah\Documents\geoloc
   python -m orthoproto align --config configs/orthoproto/geoloc_capture_01.yaml
   python -m orthoproto dsm --config configs/orthoproto/geoloc_capture_01.yaml
   python -m orthoproto ortho --config configs/orthoproto/geoloc_capture_01.yaml
   ```
   (пакет уже установлен editable: `pip install -e tools/orthoproto`, если нет — установи). Полный `ortho`-прогон занимает 20-75 минут в зависимости от того, сколько кадров проходит AGL-фильтр — можно временно снизить `patch_every_n`/добавить лимит на число кадров в `run_ortho` для быстрой итерации, но финальную проверку сделай на полном прогоне.
3. **Критерий успеха**: сравни с текущим базовым результатом (уже закоммичен, `git log` покажет коммиты `a186c3f`/`565830a`) —

   - `ortho` step: `mean lidar coverage` (сейчас 8.6%) должен вырасти заметно, особенно за счёт кадров БЕЗ AGL-фильтра или с ослабленным порогом `agl_max_m` (если глобальная оптимизация действительно чинит дрейф через разворот, эти кадры должны перестать быть выбросами).
   - Визуально: открой `data/outputs/geoloc_capture_01_ortho/ortho_mosaic.png` — размытая/раздвоенная область слева (там, где перекрываются проходы до/после разворота) должна стать заметно чище.
