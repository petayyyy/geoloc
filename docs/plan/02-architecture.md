# 02 — Архитектура

## 1. Системы координат

Следуем REP-103 / REP-105 с одним отступлением: наш глобальный фрейм — локальный ENU, привязанный к точке старта миссии.

| Фрейм | Описание | Кто публикует |
|---|---|---|
| `map_enu` | Локальный ENU, начало — заданная точка миссии (lat0, lon0, h0). **Глобально привязан** | `geoloc_fusion` |
| `odom` | Фрейм одометрии FAST-LIVO2. Гладкий, дрейфует | `fast_livo2` |
| `base_link` | Корпус аппарата | tf |
| `lidar` | Livox Avia | статический tf (калибровка) |
| `camera` | Оптический центр камеры | статический tf (калибровка) |

**Ключевая цепочка:**

```
map_enu ──[SE(2)-коррекция, публикует geoloc_fusion]──► odom ──[FAST-LIVO2]──► base_link
```

Фикс корректирует **`map_enu → odom`**, а не позу аппарата напрямую. Одометрия остаётся гладкой, вся глобальная коррекция сосредоточена в одном преобразовании. Это стандартный и единственно правильный паттерн — он же гарантирует, что скачок коррекции не превратится в скачок скорости для контура управления.

Преобразование `map_enu ↔ WGS84` — через фиксированную опорную точку (lat0, lon0, h0) и локальную касательную плоскость.

## 3. Узлы: ответственность и границы

| Узел | Отвечает за | НЕ отвечает за |
|---|---|---|
| `geoloc_ortho` | Геометрию: облако → DSM → true-ortho патч + карта уверенности | Любую работу с признаками и картой |
| `geoloc_map` | Хранение и выдачу окна подложки, DEM, OSM; кэш дескрипторов карты | Матчинг |
| `geoloc_matcher` | Признаки, соответствия, оценку SE(2), выбор канала (основной/резерв) | Принятие решения о валидности |
| `geoloc_integrity` | Решение «принять/отвергнуть» и оценку ковариации | Оценку SE(2) |
| `geoloc_fusion` | Граф факторов, глобальную позу, приорное окно | Интерфейс с автопилотом |
| `geoloc_mavlink` | Трансляцию в MAVLink, failsafe | Оценку качества |

**Принцип разделения:** `geoloc_matcher` всегда выдаёт результат с метриками качества, но **никогда** не решает, годен ли он. Решение изолировано в `geoloc_integrity` — это делает integrity-логику независимо тестируемой и заменяемой, что критично, потому что она главный предохранитель системы.

## 4. Режимы работы

| Режим | Условие входа | Поведение |
|---|---|---|
| `INIT` | Старт | Ждём одометрию и первый фикс. Приорное окно = ±R₀ (по конфигу, типично 500 м) |
| `CONVERGING` | Есть 1–4 фикса | Публикуем позу, но `fix_type=2`. Окно сужается по ковариации |
| `NOMINAL` | ≥5 фиксов, σ_ψ < 1° | Полная работа, `fix_type=3` |
| `COASTING` | Нет валидных фиксов > 20 с | Только одометрия, ковариация растёт по модели дрейфа, `fix_type` понижается |
| `LOST` | Нет фиксов > 180 с или ковариация > порога | `fix_type=0`, окно расширяется до R_max, многогипотезный поиск |
| `DEGRADED` | Основной канал провалился, работает резерв | Как NOMINAL, но с раздутой Σ и пометкой в диагностике |

Переходы и пороги — в `tasks/T25-*.md` и `tasks/T28-*.md`.

## 5. Резервные каналы матчинга

Арбитраж каналов — в `geoloc_matcher`, стратегия «основной → резерв при провале, а не параллельно всегда» (экономия бюджета).

| Канал | Когда включается | Ожидаемая точность | Стоимость |
|---|---|---|---|
| **Основной**: XFeat* + MAGSAC | Всегда | 3–6 м, курс 0.5–1.5° | 40–60 мс |
| **Резерв 1**: фазовая корреляция по градиентам (log-polar FFT → yaw+scale, затем translation) | Инлаеров <30 два кадра подряд | 5–15 м, курс 1–3° | ~20 мс |
| **Резерв 2**: семантика (сегментатор NPU ↔ растр OSM), chamfer/IoU-матчинг | Оба выше провалились, местность — поля/лес | 15–40 м, курс 2–5° | ~50 мс |

Резерв 2 никогда не выдаёт `fix_type=3` — он служит для ограничения роста ковариации, а не для точной коррекции.

## 6. Пайплайн подготовки карты (офлайн, до вылета)

```
коридор миссии (GeoJSON) ──┐
                           ├─► загрузка тайлов провайдера A (основной)
                           ├─► загрузка тайлов провайдера B (для OrthoSim и кросс-проверки)
                           ├─► загрузка Copernicus DEM 30 м
                           └─► выгрузка OSM (Overpass) → растеризация слоёв
                                       │
                   ┌───────────────────┴───────────────┐
                   ▼                                   ▼
        сборка COG-мозаики @ 0.3/0.5 м/px      растр семантики @ 1 м/px
        + пирамида уровней                     (дорога/здание/вода/поле/лес)
                   │
                   ▼
        (опционально) предвычисление дескрипторов XFeat по сетке
                   │
                   ▼
        пакет карты: <mission>.geopack (COG + DEM + OSM + манифест + bias)
```

Предвычисление дескрипторов — **опция, не база**. База: считать дескрипторы окна на борту, кэшируя их и пересчитывая при сдвиге окна >30%. Причина: предвычисление привязывает пакет карты к конкретной версии модели и раздувает его, а выигрыш на борту ~8 мс/кадр амортизированно.

## 7. Развёртывание

| Слой | Решение |
|---|---|
| ОС | Ubuntu 22.04 / 24.04 arm64 на OrangePi, ядро с драйверами RK3588 (NPU, RGA, Mali) |
| ROS | ROS 2 Humble (под 22.04) или Jazzy (под 24.04) — зафиксировать в [ADR-007](adr/ADR-007-ros-distro-os.md) |
| Сборка | Кросс-компиляция на x86 в Docker (`--platform linux/arm64`), деплой артефактом. Нативная сборка на плате — только для отладки |
| Запуск | systemd-юниты, автостарт, watchdog на каждый узел |
| Конфигурация | Единый YAML на миссию: параметры, пороги, путь к geopack |
| Логи | rosbag2 на NVMe + структурированные метрики в parquet для послеполётного анализа |
