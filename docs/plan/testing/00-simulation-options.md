# Стратегия тестирования: разбор вариантов симуляции

**Статус:** черновик на утверждение. После выбора становится `testing/00-test-strategy.md`.
**Контекст:** глобальная локализация БПЛА по спутниковой ортоподложке. Сенсоры: **Livox Avia + одна камера + IMU**, одометрия — **FAST-LIVO2** → PX4 EKF2. Борт: OrangePi 5 Pro (RK3588S). Профиль: AGL 100–150 м, маршрут 5–10 км.

---

## 0. Что изменилось после уточнения профиля

Подтверждено: на борту **Livox Avia**, данные с него идут в FAST-LIVO2. Это меняет три вещи в архитектуре и, соответственно, в тестировании.

Отдельно про Avia: FOV 70.4° × 77.2°, non-repetitive scan, дальность 190 м @ 10% отражения. На 100–150 м AGL пятно облака ~140 × 155 м при 100 м и ~210 × 230 м при 150 м — то есть **у́же кадра камеры (200 × 150 м при HFOV 90°)**. Следствие: true-ortho из лидарного DSM покрывает не весь патч. Решение — накопление облака за 0.5–1 с с deskew по одометрии (при 10 м/с это добавляет 5–10 м вдоль маршрута) плюс поддержка глобального DEM как заполнителя на краях. Это отдельная задача в плане и отдельный тест-кейс в OrthoSim.

| | Было (моно-камера, плоскостное допущение) | Стало (FAST-LIVO2 на борту) |
|---|---|---|
| Ортовыпрямление патча | Гомография по attitude+AGL+DEM 30 м. Ошибка рельефа 1–3 м, параллакс зданий не моделируется | **True-ortho по лидарному DSM 0.5–1 м.** Окклюзии и параллакс убираются геометрически, до матчинга |
| Дрейф между фиксами | Моно-VO 1–2% пути → до 200 м на 10 км | FAST-LIVO2: per-sequence ATE 0.75–3.25 м на маршрутах до 7.1 км (MARS-LVIG). **Дрейф положения перестаёт быть главной угрозой** |
| Главная угроза | Дрейф + доступность фиксов | **Начальная ошибка курса и курсовой дрейф.** ±3° на прямой 10 км = ~523 м бокового ухода. Отсюда требование ≥5 фиксов на первых 2 км |
| Вычислительный бюджет | Свободный (~1.5 ядра A76) | **Напряжённый.** FAST-LIVO2 сам по себе съедает большую часть A76-кластера. Это новый риск №1 |

**Пересмотренные системные цели** (AGL 100–150 м, 5–10 км, подложка 0.3–0.5 м):

| Метрика | Цель | Обоснование |
|---|---|---|
| Ошибка положения, p50 | < 10 м | Пол задаёт георефернция спутниковой подложки (2–5 м CE90), а не матчер |
| Ошибка положения, p95 | < 30 м | AnyVisLoc: 58.5% @20 м на спутнике; с накоплением фиксов и фильтром — реалистично |
| Курс после сходимости, p95 | < 0.5° | 0.5° на 10 км = 87 м бокового ухода — внутри бюджета 200 м |
| Фиксов на первые 2 км | ≥ 5 валидных | Математическое условие сходимости курса с ±3° до 0.15–0.2° |
| Доля ложных принятых фиксов (>50 м) | **< 0.5%** | Один принятый ложный фикс уводит EKF2. Важнее точности |
| Макс. непрерывный участок без фиксов | ≤ 3 км | При ATE FAST-LIVO2 ~1.4 м/км + курсовой дрейф |
| Такт фиксов | 1–2 Гц | Компромисс с бюджетом RK3588 |

Геометрия при 100–150 м AGL и HFOV 90°:

| AGL | Пятно | Патч @ 0.5 м/px | GSD снимка (1456 px) |
|---|---|---|---|
| 100 м | 200 × 150 м | 400 × 300 px | 0.137 м |
| 150 м | 300 × 225 м | 600 × 450 px | 0.206 м |

GSD снимка в 2–3 раза лучше подложки — запрос всегда даунсемплим к GSD карты. Это хорошо: даунсемплинг сам по себе гасит часть домейн-гэпа (мелкие детали, которых на спутнике нет).

## 1. Принцип: сначала риски, потом инструменты

Симулятор ценен ровно настолько, насколько он снимает конкретный риск. Ниже — список рисков, каждый из которых должен быть закрыт каким-то видом тестирования. Инструменты выбираем под них, а не наоборот.

| # | Риск | Почему опасен |
|---|---|---|
| **R1** | Домейн-гэп: кадр ↔ спутниковая подложка (сезон, солнце, дата съёмки, провайдер, снег, тени) | Главная причина отказов в поле. В симуляторе возникает **бесплатно и незаметно**, если текстурировать землю той же подложкой |
| **R2** | Геометрия: корректность true-ortho, лидарный DSM, параллакс зданий, рельеф | Систематические сдвиги, которые матчер не отличит от истины |
| **R3** | Качество матчера (XFeat* INT8 на RKNN) на реальном распределении данных | INT8-квантизация может обвалить точность непредсказуемо |
| **R4** | Integrity: ложные фиксы, гейтинг, модель ковариации | Опаснее отсутствия фиксов |
| **R5** | Фьюжн: SE(2)-фактор поверх FAST-LIVO2, сходимость курса, состоятельность ковариации | Плохая ковариация → EKF2 либо игнорирует фиксы, либо доверяет чрезмерно |
| **R6** | Замкнутый контур: PX4 EKF2 + `GPS_INPUT`, failsafe, задержки, переключение режимов | Известный дрейф EKF2 (issue FAST-LIVO2 #126). Ошибка здесь = потеря аппарата |
| **R7** | Рантайм на RK3588: латентность, троттлинг, память, загрузка NPU | Плата в закрытом корпусе дрона |
| **R8** | **Влезает ли FAST-LIVO2 на RK3588 вообще** | Если нет — рушится вся архитектура. Проверять первым |
| **R9** | Доступность фиксов по типам местности (город/поля/лес/вода) | Определяет маршрутные ограничения |
| **R10** | Курсовой дрейф на 5–10 км, вырождение над однородной местностью | Плоскость наблюдает только z/roll/pitch; x/y/yaw держатся на визуальном канале |

## 2. Варианты — детальный разбор

### Вариант A. Собственный офлайн-рендерер «OrthoSim»

**Что это.** Не симулятор физики, а генератор тестовых пар. Берём реальное ортофото + DSM, задаём 6-DoF позу камеры, варпим патч-запрос, инъектируем искажения. Ground truth известен **точно и бесплатно** — он задан, а не измерен.

**Главный трюк реализма.** Запрос рендерим из **одного** источника снимков, карту берём из **другого**: Esri World Imagery ↔ Bing ↔ Mapbox ↔ Google ↔ NAIP другого года ↔ Sentinel-2. Разные даты, разные сезоны, разная радиометрия, разные углы солнца — **настоящий кросс-доменный разрыв без единой строчки симулятора**. Ни один игровой движок этого честно не воспроизведёт.

**Что моделируем поверх:**
- радиометрия: гамма, баланс белого, контраст, дымка/haze;
- солнце: направленные тени по DSM (ray-cast), смена высоты солнца;
- сезон: подмена источника + цветовой перенос, снежные маски;
- геометрия: ошибки attitude (0.1–1.0°), AGL (0.5–5%), рассинхрон времени;
- сенсор: шум, размытие в движении, виньетирование, JPEG-артефакты;
- лидарная ветвь: синтез облака точек из DSM с паттерном сканирования и шумом дальности → проверка цепочки «облако → локальный DSM → true-ortho».

**Закрывает:** R1 (отлично), R2, R3, R4, R9
**Не закрывает:** R5, R6 (нет замкнутого контура), R7, R8

**Трудозатраты:** v1 — 5–7 дней (rasterio + OpenCV + пул тайлов). +5 дней на DSM/тени/синтез облака.
**CI:** идеально. CPU-only, детерминированно по сиду, тысячи семплов за минуты, гоняется на каждый коммит.

> **Оценка: главная рабочая лошадь.** Лучшее отношение ценности к трудозатратам во всём списке. Здесь тюнятся пороги, гейтинг и модель ковариации.

> **ВЫБРАН.** См. `01-test-strategy.md`.

---

### Вариант B. Реплей реальных датасетов

**Что это.** Прогон настоящих полётных логов через реальный ROS 2-граф — сначала на x86, потом на самой OrangePi.

**Датасеты:**

| Датасет | Что даёт | Роль |
|---|---|---|
| **MARS-LVIG** | Livox Avia + global-shutter камера (hw-sync 10 Гц) + IMU + RTK, 80–130 м, до 7.148 км, 3–12 м/с | **Основной.** Единственный с лидар + надир + RTK в нашем диапазоне высот. Прямо под FAST-LIVO2 |
| **UAVScenes** (ICCV 2025) | Те же данные + семантика + 6-DoF позы | Для семантического резервного канала |
| **OrthoLoC** | UAV-снимки + DOP 5 см + DSM + RTK/GCP (3D RMSE ~5 см) | Отработка матчинга DOP↔true-ortho, AdHoP, PnP |
| **AnyVisLoc / UAV-AVL** | 20 077 снимков DJI, 24 сцены, 30–300 м, аэро- и спутниковая подложка | Количественное сравнение Tier1/Tier2, только матчер |
| **UAV-VisLoc, VPAIR** | Снимки + спутниковая подложка | Дополнительная выборка сцен |

**Нюанс:** у MARS-LVIG нет встроенной подложки — её надо **дозагрузить самим** (спутниковые тайлы на районы HK/AM) и выровнять по RTK-траектории. Это отдельная задача на 3–5 дней, и она же вскроет реальную величину георефернционного bias подложки.

**Закрывает:** R1, R3, R4, R9, R10; на плате — R7, R8
**Не закрывает:** R6 (только разомкнутый контур)

**Трудозатраты:** 1.5–2 недели (загрузка, подложки, выравнивание, харнесс метрик).
**CI:** частично — короткие нарезки (по 200–500 м) как регрессия в ночном прогоне; полные последовательности — по требованию.

> **Оценка: обязателен, не обсуждается.** Это единственная честная цифра точности. Всё остальное — прокси.

> **ВЫБРАН.** См. `01-test-strategy.md`.

### Вариант C. Gazebo Harmonic (gz-sim) + PX4 SITL

**Что это.** Замкнутый контур: мир из Copernicus DEM (heightmap) + ортотекстура коридора, модель дрона, камера, лидар, PX4 SITL, MAVROS, наш стек.

**Что здесь реально проверяется — и что нет.** Это ключевой момент. Если текстурировать землю той же подложкой, по которой идёт матчинг, домейн-гэп **равен нулю**, и метрика точности получится фантастической и бессмысленной. Поэтому Gazebo у нас проверяет **не матчинг, а систему**:
- поведение PX4 EKF2 при подаче `GPS_INPUT` с честными `eph/epv`;
- реакция на потерю фиксов, на скачок ковариации, на **намеренно подсунутый ложный фикс**;
- failsafe, переключение режимов, задержки в контуре управления;
- поведение при холодном старте и при «похищении робота».

**Специфика лидара.** `gz-sim` умеет `gpu_lidar`, но это вращающийся паттерн. **FAST-LIVO2 рассчитан на non-repetitive scan Livox** — нужен отдельный плагин (форки `livox_laser_simulation` под Ignition/Harmonic). И даже с ним: в симуляции нет motion distortion, реальной интенсивности и атмосферы — **результаты FAST-LIVO2 из Gazebo на реальность не переносятся**. Одометрию валидируем на MARS-LVIG (вариант B), а в Gazebo лидар нужен лишь чтобы граф не разваливался.

**Закрывает:** R5, R6 (единственный, кто закрывает R6), частично R2
**Не закрывает:** R1 (принципиально), R3, R4, R7, R8, R9

**Трудозатраты:** 2–3 недели (генератор мира из DEM+ортофото, модель аппарата, лидарный плагин, MAVROS-мост, сценарии).
**CI:** headless — да, но тяжело: минуты на прогон, для рендера камеры нужен GPU (софт-рендер работает, но медленно).

> **Оценка: обязателен ради R6, но только ради него.** Не позволять ему разрастаться в «главный полигон» — это самая частая ошибка в таких проектах.

### Вариант D. Blender / Cycles — офлайн фотореалистичный рендер

**Что это.** Меш из DSM + ортотекстура, рендер пролёта по коридору при контролируемых условиях: высота солнца 10/30/60°, облачные тени, снег, дымка, время суток. Не realtime — рендерим один раз на ваших 4090, кладём последовательности как фикстуры.

**Что даёт сверх варианта A:** физически корректные тени и глобальное освещение, реальная 3D-геометрия зданий (параллакс, окклюзии), контролируемый свип по одному параметру при фиксированных остальных. Вариант A даёт домейн-гэп «как в жизни, но неуправляемый»; вариант D — «управляемый, но синтетический». Они дополняют друг друга.

**Закрывает:** R1 (контролируемо), R2 (точно)
**Не закрывает:** R3–R10

**Трудозатраты:** 1–1.5 недели.
**CI:** нет — только как фиксированный набор фикстур.

> **Оценка: полезное, но не первоочередное дополнение.** Брать, если нужен количественный ответ «при каком угле солнца система ломается».

### Вариант E. Isaac Sim

Фотореализм максимальный, RTX-лидар умеет кастомные паттерны (включая Livox-подобные) через конфигурационные профили, ROS 2-мост есть, PX4 SITL подключается.

**За:** закрывает **C и D разом** — и замкнутый контур, и управляемый фотореалистичный свип по солнцу/сезону/погоде. RTX-Lidar с non-repetitive профилем решает задачу модели Avia **конфигурацией, а не написанием плагина** — это дешевле, чем Livox-плагин под Gazebo. Отдельный Blender-трек становится не нужен.

**Против:** RTX-карта нужна на каждый прогон, порог входа высокий, импорт георефернцированного терраина требует пайплайна DEM → USD, per-commit CI неподъёмен.

> **ВЫБРАН.** У заказчика есть 5×RTX 4090 и DGX Spark — главное возражение снимается. Isaac заменяет варианты C и D.
>
> **Условие:** per-commit CI остаётся на варианте A (OrthoSim, CPU). Isaac-сценарии гоняются **ночным прогоном** на GPU-машине, а не на каждый коммит.
>
> **Существующий Gazebo-стенд** с дроном сохраняется как опциональный быстрый smoke-тест контура (задача T30-opt, низкий приоритет). Вкладываться в Livox-плагин под Gazebo не нужно — 30-метровый лидар оставить, эти прогоны не про лидар.

### Вариант F. AirSim / Colosseum

AirSim заархивирован (2022), Colosseum — полуживой форк на UE5. Модель лидара упрощённая, георефернция терраина ручная, CI тяжёлый.

> **Оценка: не брать.** Ничего не даёт сверх C+D.

### Вариант G. Flightmare / FlightGoggles / gym-pybullet-drones

Быстрая динамика, но георефернцированного терраина и серьёзного лидара нет.

> **Оценка: не брать** для этой задачи.

---

### Вариант H. HIL — плата в контуре

**Что это.** OrangePi 5 Pro крутит настоящий стек; данные подаются либо реплеем (вариант B), либо из Gazebo по сети; результат уходит в PX4 SITL.

**Закрывает:** R7, R8 + всё, что даёт источник данных.

Отдельно: **бенч-сьют на плате** — латентность p50/p95 по каждой стадии, загрузка NPU/GPU/ядер, потребление, температура и троттлинг под 30-минутной нагрузкой в корпусе, пиковая память.

**Трудозатраты:** 1 неделя (сетевой мост, синхронизация времени, сбор телеметрии).
**CI:** self-hosted runner на плате, ночной прогон.

> **Оценка: обязателен.** Это единственный способ узнать, влезает ли FAST-LIVO2 + XFeat в бюджет RK3588. И узнать это надо **на первой-второй неделе**, а не на пятом месяце.

## 4. Рекомендация и принятое решение

> **ПРИНЯТО: A + B + E**, где E (Isaac Sim) занимает место C и D.
> HIL перестал быть отдельным уровнем: FAST-LIVO2 **уже запущен на OrangePi 5 Pro по bag**, поэтому прогон на плате — это способ исполнения уровней A и B, а не отдельная ступень. Риск R8 снят, остаётся измерить остаточный бюджет (задача T31).
> Ниже — исходная рекомендация с вариантом C; она сохранена для истории решения, фактический план в `01-test-strategy.md`.

**Ядро: A + B + H + C**, именно в этом порядке приоритета.

```
Неделя 1–2   H (bare-metal бенч)  ──► ответ на R8: влезает ли FAST-LIVO2 на RK3588
             ↑ САМОЕ ПЕРВОЕ. Если не влезает — архитектура меняется, план переписывается.

Неделя 1–3   A (OrthoSim)         ──► CI на каждый коммит, тюнинг матчера и порогов
             ║ параллельно
Неделя 2–4   B (реплей MARS-LVIG) ──► честные цифры точности и доступности фиксов
             ║ параллельно
Неделя 4–7   C (Gazebo + PX4)     ──► замкнутый контур, failsafe, integrity в контуре

Опция        D (Blender)          ──► свип по солнцу/сезону, если понадобится число
```

**Почему такой порядок.** R8 — экзистенциальный риск: если FAST-LIVO2 не идёт на RK3588 с приемлемым тактом, весь остальной план не имеет смысла. Его проверка не требует ни симулятора, ни матчера — только плату, датасет и профайлер. Это дёшево и должно быть сделано первым.

**Чего не берём:** Isaac Sim, AirSim/Colosseum, Flightmare — покрытие рисков не оправдывает трудозатрат.

**Поверх пирамиды, на всех уровнях:**
- property-based юнит-тесты геометрии (round-trip варпа, преобразования координат, проекции) — `hypothesis`;
- golden-run регрессия: зафиксированные траектории + допуски на метрики, падение CI при деградации;
- fault injection: пропажа фиксов, ложный фикс, окклюзия камеры, скачок AGL, шум IMU, деградация лидара;
- Monte-Carlo по сидам для фьюжна (100+ прогонов, проверка состоятельности ковариации через NEES/NIS).

## 5. Метрики (единые для всех уровней)

**Уровень фикса**

| Метрика | Целевое значение |
|---|---|
| A@5 / A@10 / A@20 / A@50 м | ≥15% / ≥35% / ≥60% / ≥85% (город/пригород) |
| Курсовая ошибка на фикс, медиана / p95 | ≤1.0° / ≤2.5° |
| Число инлаеров MAGSAC | ≥30 для принятия |
| Covisibility | ≥20% (гейт по покрытию, из OrthoLoC) |
| **Integrity failure rate** (принят, но ошибка >50 м) | **< 0.5%** |
| Fix acceptance rate по классам местности | город ≥60%, поля ≥25%, лес ≥8% |

**Уровень траектории**

| Метрика | Целевое значение |
|---|---|
| ATE RMSE на 5–10 км | ≤ 15 м |
| p95 бокового ухода | ≤ 30 м |
| Курсовая ошибка после сходимости, p95 | ≤ 0.5° |
| Фиксов на первые 2 км | ≥ 5 валидных |
| Time-to-first-fix (приор ±500 м) | ≤ 10 с |
| Время восстановления после 2-км аутэйджа | ≤ 30 с |

**Уровень рантайма (RK3588)**

| Метрика | Целевое значение |
|---|---|
| Латентность фикса, p95 | ≤ 300 мс |
| Такт FAST-LIVO2 | ≥ 10 Гц устойчиво |
| Загрузка CPU (8 ядер) | ≤ 70% средняя |
| Температура SoC под 30-мин нагрузкой | ≤ 80 °C, без троттлинга |
| Пиковая RSS | ≤ 4 ГБ |
